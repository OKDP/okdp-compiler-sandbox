# OKDP deployments layout (bootstrap)

This directory bootstraps the desired state of an OKDP platform: the **tree** of its
deployments, [okdp-compiler](https://github.com/OKDP/okdp-compiler)'s (`platform.yaml`,
`projects/`), the files [okdp-gitops](https://github.com/OKDP/okdp-gitops) keeps beside
it (`catalogs.yaml`), and the entry points of the engines (`argocd/`, `flux/`). Every
instance is **compiled** into what Helm installs, the same under both engines: the
people and the console write the tree, a compile writes `compiled/`, and the engines
deploy `compiled/`. `scripts/configure.sh --push` compiles the committed layout and
puts the tree and the compiled tree on the sandbox's Forgejo, which holds the **only
desired state** from then on: the console (through the control plane server) and the
people commit the tree there, the **CI** of the output repository compiles the
latest tree into the output every 2 minutes (okdp-gitops, on the Forgejo Actions
runner of the bootstrap,
[`forgejo-runner`](https://github.com/OKDP/sandbox-charts/blob/main/bootstrap/forgejo-runner/values.yaml)), and Argo CD
**or** Flux deploys it. The compiled tree is never in this repository. An instance
names a **package** of a service catalog (a Git repository, [below](#service-catalogs)),
which okdp-compiler compiles into an umbrella chart over the upstream charts of the
service, with its values. Nothing OKDP is pulled from a chart registry.

The platform's dependencies (Keycloak, the S3 store, CloudNativePG, External Secrets,
OpenBao, Forgejo, the engine) are not in the tree: they are installed with Helm before
anything compiled ([`bootstrap/`](https://github.com/OKDP/sandbox-charts/tree/main/bootstrap), README step 3), and the tree reaches
them through the platform's settings and connections ([`platform.yaml`](#platformyaml)).

On Forgejo, the tree lives in a platform repository and a projects repository (`io`,
a small team) or a repository per project (`split`), the compiled tree in an output
repository of its own, which the CI alone writes: the **topology**
([below](#topologies)), chosen with `scripts/configure.sh`.

## Layout

```
platform.yaml                     # the platform: global.okdp, the classes of the claims, the
                                  # platform's connections; the context of every instance (level 0)
catalogs.yaml                     # okdp-gitops': the service catalogs (repositories), the console menu
projects.yaml                     # okdp-gitops', split topology only: the projects, one repository each
projects/<p>/                     # a project: the namespace <p>
  project.yaml                    #   its context (level 1): global, classes, connections, named claims
  instances/<i>/                  #   an instance: the release <p>-<i>
    instance.yaml                 #     {service, version}: its package
    config.yaml                   #     its values: the package's parameters, upstream values
    connections.yaml              #     rare: its own connections (level 2)
compiled/                         # generated by okdp-gitops compile, in the output repository
                                  # only (not here): never edit
  projects/kustomization.yaml     #   Flux: the projects
  projects/<p>/kustomization.yaml #   Flux: the instances of the project and its manifests
  projects/<p>/project/           #   the project's manifests: its Namespace, its SecretStore,
                                  #   the identity of its releases (Generated files)
  projects/<p>/instances/<p>-<i>/ #   the compiled instance, its engine files (Generated files)
argocd/                           # Argo CD entry point (reads the output repository)
  project.yaml                    #   AppProject okdp (the entry point)
  root.yaml                       #   Application okdp (manages argocd/ itself); okdp-gitops reads
                                  #   its source, the repository of the Applications it writes
  instances.yaml                  #   Application okdp.instances: the instances' Applications
  projects.yaml                   #   ApplicationSet okdp.projects: the projects' manifests,
                                  #   compiled/projects/<p>/project/ (an AppProject per project)
  ingress.yaml                    #   Argo CD's UI at https://argocd.okdp.sandbox
  bootstrap/                      #   patches of the Argo CD configuration (applied once, by hand):
    argocd-cm-patch.yaml          #     the health of Applications, the sign-in with Keycloak
    argocd-rbac-cm-patch.yaml     #     the Argo CD roles of the Keycloak users
flux/
  sync.yaml                       # Flux entry point, applied at the bootstrap: GitRepository
                                  # okdp-gitops (the output repository), Namespace okdp-releases,
                                  # Kustomization okdp of ./compiled/projects
optional/projects/                # projects and instances not deployed, moved into place by hand
```

There are no platform components and no layers: the platform's own services (the
database server, the Spark operator, the control plane...) are instances of projects
without user members, `projects/<namespace>/instances/`, and
the deployment graph (connection references, claims) is the only order; an instance
applied before the CRDs of its operator is retried by the engine. The
[scripts](#scripts) that configure, compile, check and push this layout are at the root
of the repository, in `scripts/`. The platform's prerequisites (cert-manager,
ingress-nginx, the DNS, the tools, the operators of the databases and of the secrets,
Keycloak, the S3 store, OpenBao, Forgejo and its CI runner) are no projects: the
bootstrap installs them with Helm (README, step 3).

| Project (namespace) | Instances |
|---|---|
| `default` | `spark-rbac` |
| `spark-operator` | `spark-operator` |
| `cnpg-system` | `cnpg-postgresql`, the platform's database server (the provider of the claims of databases) |
| `s3-system` | `s3-minio-provisioner`, the provider of the claims of buckets on RustFS of the bootstrap (its connection `rustfs`, of `project.yaml`) |
| `okdp-system` | `okdp-control-plane-server`, `okdp-control-plane-ui`, `local-secrets-provider` |
| `demo` | `airflow`, `hive`, `jupyterhub`, `polaris`, `secrets`, `spark-history`, `superset`, `trino` |

The platform's own projects are listed in `global.okdp.policy.privileged` of
[`platform.yaml`](platform.yaml): `spark-operator`, `okdp-system`, and the optional
operators, once moved into place, whose instances install cluster-scoped objects (CRDs, cluster roles,
webhooks), write other namespaces or run privileged pods, with the engine's own
identity, in namespaces that admit privileged pods. Every other project, the
platform's `cnpg-system`, `s3-system` and `default` among them, is confined to its
namespace by okdp-compiler: its objects in its namespace only, no cluster-scoped
kind, its releases installed under an AppProject of its namespace (Argo CD) or with
an identity of its namespace (Flux), Pod Security `baseline` enforced
([Generated files](#generated-files)).

The bootstrap's cert-manager and ingress-nginx can be replaced by the cluster's own:
the services and the dependencies name them by the platform's settings only
(`global.okdp.ingress.className`, `global.okdp.tls.clusterIssuer`,
`global.okdp.tls.caBundleSecret`); the CoreDNS patch names the controller's Service
(`INGRESS_SERVICE` of sandbox-charts' `bootstrap/coredns/patch.sh`).

Names used below: `<p>` project, `<i>` instance, `<r>` = `<p>-<i>` the Helm release
name, `<c>` a connection name.

## Topologies

Each part of the layout lives in a repository of the sandbox's Forgejo (organization
`okdp`, `http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/<repository>.git`,
branch `main`), the output always in a repository of its own:

| Part | Content | `io` (the default) | `split` |
|---|---|---|---|
| platform | `platform.yaml`, `catalogs.yaml`, `projects.yaml` (split) | `okdp-platform`, its root | `okdp-platform`, its root |
| project `<p>` | `project.yaml`, `instances/` | `okdp-projects`, `projects/<p>/` | `okdp-project-<p>`, its root |
| output | `compiled/`, `argocd/` | `okdp-output`, its root | `okdp-output`, its root |

There is no topology of one repository for the sources and the output (the former
`mono`): Forgejo grants write access per repository, not per path, and a writer of
the output deploys anything, past every check of the compile. The repository is the
unit of write permission, without the control plane: who writes a repository writes
every file of it. Hence **who can do what**:

- **the output** (`okdp-output`): the CI's account `okdp-gitops` alone pushes to its
  `main` (a protected branch, its push whitelist), with the only token of the CI,
  the output repository's own; the engines read it only. Nobody else writes it, the
  admin and the people included.
- **the platform** (`okdp-platform`, in both topologies): `platform.yaml` (the
  platform's settings, the classes of the claims, the privileged projects, the
  secret store) and `catalogs.yaml` (what may be deployed), the platform admins'
  alone. Kept apart in io too: the team's write access stops at the projects.
- **io, for a small team**: one repository for every project, `okdp-projects`. Every
  writer of it writes every project, the platform's own ones among them
  (`okdp-system`, the operators, the database server: privileged projects), so every
  writer is trusted with all of them. `scripts/check.sh` warns of it.
- **split, for bigger deployments**: a repository per project, `okdp-project-<p>`,
  written by its team only; the permissions are per repository, per project. The
  levels the compiler enforces (a project sets only what a project may set, an
  instance never `global.okdp`) hold the platform's settings against a project's
  files; the privileged projects' repositories are the platform admins'.

In both, the sources hold no token and no workflow, the CI is the output
repository's, and the control plane, when installed, writes the sources only (in the
sandbox it still signs in as `okdp-gitops`, the CI's account, until it gets one of its
own).

- **Argo CD and Flux read the output repository only**: `argocd/` and `flux/sync.yaml`
  name it, and their paths are at its root (`./compiled/projects`) in every topology.
- The control plane server reads the topology from its values
  ([`okdp-control-plane-server`](projects/okdp-system/instances/okdp-control-plane-server/config.yaml)),
  `gitops.topology`, required (there is no single repository, `gitops.repoURL`, any
  more), its topology file (`GITOPS_CONFIG`), which gives each part:

  ```yaml
  topology:                                                                            # io
    platform: {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-platform.git, branch: main, path: ""}
    projects: {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-projects.git, branch: main, path: "projects/{project}"}
    output:   {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-output.git, branch: main, path: ""}
  ```

  ```yaml
  topology:                                                                            # split
    platform: {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-platform.git, branch: main, path: ""}
    projects: {url: "http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-project-{project}.git", branch: main, path: ""}
    output:   {url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/okdp-output.git, branch: main, path: ""}
    forgejo:  {url: http://forgejo-http.forgejo.svc.cluster.local:3000, owner: okdp}
  forgejoTokenSecret: okdp-forgejo-token
  ```

  `okdp-gitops compile --config <file>` reads the same file (a `url` may also be a
  local directory, read and written in place); `platform.path` is the directory of
  `platform.yaml`. okdp-gitops refuses a topology whose output is a repository of the
  sources.
- A change, the console's or a person's, is a commit of the tree (platform or project
  repository); the next run of the CI of the output repository, every 2 minutes,
  compiles it into the output repository (`okdp: compile`, from the latest tree of
  every part, and `sources.yaml`, the revisions it compiled; a run whose sources did
  not move stops early), which the engines deploy. A change that does not compile
  writes no output (the console refuses it before it commits). `okdp-gitops compile
  --check` fails while the output is stale. The CI reads the same topology file,
  without its `forgejo` section, carried by the workflow of the output repository,
  the only workflow (`okdp-gitops workflow --for output`, which
  `scripts/configure.sh --push` writes); the runner (`forgejo/forgejo-runner`, the
  bootstrap's) has none. The repositories of the sources hold no workflow and no
  token: whoever pushes a workflow to a repository reads its secrets, and a token
  that writes the output deploys anything, past every check of the compile.
- `split`: `projects.yaml` lists the projects (`projects: [{name: demo}]`, a project may
  override the `url`, `branch` or `path` of the template), every project of the
  platform's among them, a repository each. The console creates a project's repository
  `okdp/okdp-project-<p>` through the Forgejo API (the token of Secret
  `okdp-forgejo-token`, of the user `okdp-gitops`, mounted at
  `/etc/okdp/forgejo/token`), pushes its `project.yaml` (no workflow, no secret, no
  runner: the next run of the output's CI compiles it), and adds it to
  `projects.yaml`.

**This directory holds the tree and the entry points of every topology**, never the
compiled tree: the topology changes where each part is pushed, the URL of `argocd/` and
`flux/`, `gitops.topology` of the server, and `projects.yaml`; the compile happens at
the push. `scripts/configure.sh` does both steps:

```sh
scripts/configure.sh --topology io      # or -i; edits the layout
git add -A gitops && git commit -m "chore: configure the sandbox"
scripts/configure.sh --push             # the dependencies installed (README, step 3)
```

`--topology io|split` writes `gitops.topology` and, for split,
`gitops.forgejoTokenSecret` (an older layout's `gitops.repoURL`, `branch` and `path`,
the single repository of the former mono, removed); points `argocd/` and `flux/` at
the output repository, `okdp-output`; writes (split) or removes `projects.yaml`.
`--show` prints the topology and its repositories.

`--push` compiles the committed layout (`HEAD`) into the output tree, as
[`scripts/compile.sh`](#compiling-from-the-tree-to-compiled) does (nothing is pushed
when it does not compile), and puts it on Forgejo, through a `kubectl port-forward` of
the current context (or `FORGEJO_URL`), with the admin account of Forgejo
([`bootstrap/forgejo`](https://github.com/OKDP/sandbox-charts/blob/main/bootstrap/forgejo/values.yaml): Secret
`forgejo/okdp-forgejo-admin`, README step 3): it creates the organization `okdp` and
the repositories (private: the engines read the output with a read token of
`okdp-gitops`, Secret `okdp-gitops-reader` of `argocd` and `flux-system`; the
console and the CI read the sources and the catalogs as `okdp-gitops`), copies the
[service catalogs](#service-catalogs), then pushes:

| | io | split |
|---|---|---|
| tree | `platform.yaml`, `catalogs.yaml` to `okdp-platform`, `projects/` to `okdp-projects` | `platform.yaml`, `catalogs.yaml`, `projects.yaml` to `okdp-platform`, `projects/<p>/` to `okdp-project-<p>` (each project of `projects.yaml`) |
| output | `compiled/`, `argocd/` to `okdp-output` | the same |
| CI | in the output repository only: `.forgejo/workflows/okdp-gitops.yaml` (`GITOPS_INSECURE_HTTP_HOSTS='*.svc.cluster.local' okdp-gitops workflow --for output --config <topology>`: every 2 minutes and on dispatch, the topology in it, the token sent over `http://` to the cluster's services only, which the job's environment allows), its Actions enabled, its Actions secret `OKDP_GITOPS_TOKEN` a token of the user `okdp-gitops` (`write:repository`), the only token of the CI; the runner `okdp-gitops` registered for it only, never a repository of the sources nor the organization (`forgejo forgejo-cli actions register --scope okdp/<output>`, a random secret, kept in Secret `forgejo/okdp-runner-registration`, key `<output>`); its `main` protected, `okdp-gitops` alone pushing there (push whitelist), no force push. The repositories of the sources: no workflow, no secret (an older sandbox's deleted), Actions off | the same |
| writer | the user `okdp-gitops`, not an admin, in the team `okdp-gitops` that writes to `okdp-platform`, `okdp-projects` and `okdp-output` (the only account its `main` takes) and the team `okdp-gitops-read` that reads the catalogs; its random password in Secret `okdp-gitops-bot` of `okdp-system` (the console), a token of it in the output repository's `OKDP_GITOPS_TOKEN` (the CI) | the same, writing to `okdp-platform`, the `okdp-project-<p>` and `okdp-output`, and allowed to create repositories |
| token | | a Forgejo access token of `okdp-gitops` for the server, in Secret `okdp-system/okdp-forgejo-token` (key `token`) |

Each repository gets its part's files as one commit on top of its `main`
(`okdp-sandbox <sha>: <subject>`); `--push` refuses when someone committed there since
(the console, a person; the CI's compiles, `okdp: compile`, excepted: bring their
changes into this repository first), unless `--force`, which replaces them. A push of
the output that loses the race against the CI (which compiles the tree just pushed)
is made again on top of it. The sources are pushed as the admin, the output as
`okdp-gitops`, the only account its `main` takes. `--dry-run` compiles, prints what
would be done and keeps the parts it would push. The output pushed this way
bootstraps the sandbox; from then on, the CI compiles the tree on its schedule.

The console still writes the sources as `okdp-gitops`, the CI's account: whoever
reads its Secret can push the output too, until the console gets a Forgejo account
of its own, which writes the sources only.

## Service catalogs

The packages of the instances come from Git repositories, the catalogs, listed in
[`catalogs.yaml`](catalogs.yaml), okdp-gitops' file (the compiler does not read it):

```yaml
repositories:
  - name: platform-charts         # OKDP/platform-charts: the data services, the control plane
    url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/platform-charts.git
    ref: feat/claim-provisioner   # a branch or a tag
  - name: sandbox-charts          # OKDP/sandbox-charts: the sandbox's platform services, the
    url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/sandbox-charts.git
    ref: feat/claim-provisioner   # provider of the claims of databases; optional ones
  - name: community-charts        # OKDP/community-charts: community services, their operators
    url: http://forgejo-http.forgejo.svc.cluster.local:3000/okdp/community-charts.git
    ref: feat/claim-provisioner
```

A catalog holds `catalog/<service>/<version>/` (one package version, immutable once
released: `Chart.yaml`, `okdp.yaml`, `values.cel.yaml`, `config.schema.json`, the
defaults of its charts) and `contracts/<contract>.schema.json`, the contracts of the
connections. A service name is unique across the catalogs; the contracts are the union
of their `contracts/` (one contract in two catalogs is the same file). The console's
menu (`categories`) names the services; a service's versions are its directories at
`ref`, the highest offered unless the entry sets `default`. sandbox-charts also offers
the package seaweedfs, which the sandbox does not use (it installs its own S3 store,
RustFS, with Helm): a project may deploy it as an instance.

`scripts/configure.sh --push` copies each catalog that lives on the sandbox's Forgejo
from its source, at its `ref`. The scripts that compile read the catalogs from the
same sources: `--catalog <name>=<dir|url>` (or `OKDP_CATALOGS="<name>=<src> ..."`), a
directory being read as it is (uncommitted changes included, but `--push` copies its
`ref`); else the checkout `<name>` next to this repository, read at `ref` whatever is
checked out; else `https://github.com/OKDP/<name>.git` at `ref`.

## Files written by people and by the console

The files of the tree are okdp-compiler's
([repository layout](https://github.com/OKDP/okdp-compiler/blob/main/docs/01_usage.md#repository-layout)),
read as the compiler reads them; okdp-gitops writes the console's changes
([what the control plane writes](https://github.com/OKDP/okdp-gitops/blob/main/docs/specs/01_layout.md#what-the-control-plane-writes)).

### `platform.yaml`

The platform, reviewed with it: the context of every instance (level 0), which no
project and no instance may change. `global.okdp`, the platform's settings: the
ingress (`ingress.suffix`, `ingress.className`), TLS (`tls.clusterIssuer`, the
cert-manager ClusterIssuer of the services' certificates; `tls.caBundleSecret`, the
Secret of the platform's CA bundle the services mount), the OIDC provider (`oidc`, the
Keycloak of the bootstrap), the proxy, the storage classes, the classes of the claims
(`provisioning`, [Claims](#claims)) and the platform's secret store (`secrets`:
`store`, the name of the SecretStore the compiler writes in each project's namespace,
`provider`, External Secrets' provider of it, the OpenBao of the bootstrap, and
`serviceAccount`, the ServiceAccount of the namespace it signs in with), the
platform's own projects (`policy.privileged`, [Layout](#layout)); then `connections`,
the platform's connections ([Connections](#connections)). A dependency of the
platform is reached through these settings and connections, never compiled.

### `projects/<p>/project.yaml`

A project is a directory of `projects/` with a `project.yaml`, the context of its
instances (level 1): its settings under `global` (`global.okdp.project`, which the
packages may read), its classes of claims beside the platform's
(`global.okdp.provisioning`), its connections, and its named claims, connections
declared once and shared by its instances:

```yaml
description: Demonstration project, full data chain
claims:
  shared-db:                      # a DNS label, no connection's name
    contract: database-server     # the contract of its connection
    class: standard               # optional: a class of the platform or the project, else the default
    request: {extensions: [vector]}  # optional: what it requests (the contract's x-okdp-claim)
```

Its `description` is the project's own, which the console shows: okdp-compiler leaves
it out of the context of the project's instances. The directory name is the project,
the namespace of its instances. A project adds values, it changes none of the
platform's. The sandbox's projects declare little more than their description: the
demo's services claim databases of their own and use the platform's S3 connection;
`s3-system` declares the connection of its provisioner to RustFS (`rustfs`, its
credentials the provisioning identity, the key `s3-system/s3-provisioner`).

### `projects/<p>/instances/<i>/instance.yaml`

```yaml
service: trino                    # a package of the catalogs: catalog/<service>/<version>/
version: 480.0.0-1.0.0            # its version (a YAML string)
claimers: [demo]                  # rare, a provider's: the namespaces that may claim of it
```

`service` and `version`, and, for a provider, `claimers`, nothing else: the directory
names the instance, its project directory the namespace, and the release is
`<p>-<i>`. Rules (enforced by the compile and by `scripts/check.sh`):

| | rule |
|---|---|
| keys | `service` and `version`, YAML strings (tag `!!str`: quote a version such as `"6.10.0"` only if needed; `6.10` unquoted is a float and is rejected); `claimers`, optional |
| `claimers` | a provider's consent ([Claims](#claims)): a list of namespaces, DNS labels, or `"*"`, every namespace; it replaces its package's (`provisions`) |
| `service`, `version` | a package: `catalog/<service>/<version>/` of one catalog; `version` exact, `^[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z][-0-9A-Za-z.]*)?$` |
| `<p>`, `<i>` | DNS labels `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$` |
| release `<p>-<i>` | at most 53 characters; unique across projects |

The Argo CD Applications share `argocd` and the Flux HelmReleases `okdp-releases`,
named `<p>-<i>`: two pairs that concatenate to the same name (project `a-b` instance `c`
and project `a` instance `b-c`) collide, and the compile rejects the tree.

### `config.yaml`

The instance's values, optional: the parameters of the package (its
`config.schema.json`, the console's deployment form; the console writes the submitted
ones), and `upstream: {<key>: ...}`, values of one upstream chart of the package (its
dependency key), over what the package computes, except the paths the package
protects (its `okdp.yaml`, `upstream.<key>.protect`). Never `global.okdp`,
`connections` or `claims`: they are the context's. A parameter naming a connection
(`x-okdp-connection-ref` in the schema) holds the name of a connection (the
platform's, its project's, its own), of an output another instance of the project
publishes (`hive`, the output of the hive metastore, named after the instance: a
provider publishes its connections, none is computed from a name), or of a named claim of the
project: the instance then waits for that instance, or the claim's provider. A
reference that takes claims (a `database-server` one) may claim its connection
instead, a map in place of the name: `{}` (a database of its own, of the default
class), `{class: <class>}`, `{provider: <namespace>/<instance>}`, each with a `request`
(the contract's `x-okdp-claim`); the packages that need a database of their own claim
it by default, left out of `config.yaml` ([Claims](#claims)). No package claims a
bucket by default: an `s3` reference names a connection, the platform's
`platform-s3` in the sandbox.

### `connections.yaml`

Rare: the instance's own connections (level 2), `connections: {<c>: {...}}`, beside
its project's and the platform's, changing none of theirs.

## Connections

A connection is declared in `platform.yaml` (every instance may reference it),
`project.yaml` (its project's instances) or an instance's `connections.yaml`, each an
entry `connections.<c>`, `<c>` a DNS label:

```yaml
connections:
  platform-s3:                    # = <c>
    contract: s3                  # a contract of the catalogs: database-server | s3 | hive | iceberg-catalog | trino ...
    description: The platform's S3 store, RustFS of the bootstrap
    apiUrl: https://s3.okdp.sandbox  # the non-secret fields of the contract
    internalUrl: http://rustfs-svc.rustfs.svc.cluster.local:9000
    region: us-east-1
    bucket: okdp
    pathStyle: true
    secretRef:
      remoteKey: platform/s3      # its credentials: a key of the platform's secret store
```

Its credentials, the secret fields of its contract, are a Secret of the referencing
instance's namespace (`secretRef: {name: <secret>}`) or a key of the platform's secret
store (`secretRef: {remoteKey: <key>}`, `global.okdp.secrets`), each secret field a
property of it: the compiler then gives each instance that references the connection
an ExternalSecret of that key, into the Secret `<release>.<c>-credentials` of its
namespace, which its package reads as any connection's `secretRef.name`
([okdp-compiler](https://github.com/OKDP/okdp-compiler/blob/main/docs/specs/01_inputs_outputs.md#credentials-in-the-platforms-secret-store)).
This is how the platform talks to a store it neither deploys nor manages: the
platform's keys are under `platform/`, which every namespace reads and the bootstrap
writes (the sandbox's S3 store, RustFS, generates the platform's access key, and
OpenBao's init copies it under `platform/s3`, fields `accessKey` and `secretKey`; the
secrets of the Keycloak realm's clients are no platform keys: it writes each under
`<namespace>/keycloak/<client>` of the namespaces that read it, which
`local-secrets-provider` reads there, `remoteKey`); a
company's own S3 takes its place with its fields and its key in the store. A
project's own connection may only name a key of its namespace, `<p>/<key>`: the
store's policy allows nothing else ([Claims](#claims)).

`check.sh` validates each connection against `contracts/<contract>.schema.json` of the
catalogs (unknown fields, secret fields present, required non-secret fields missing,
`secretRef` a `name` or a `remoteKey`); the compile checks each connection against the
contract the parameter that names it expects, and what the parameter requires of it.

## Claims

A claim is a connection an instance asks of the instance that provisions its contract
(its package's `provisions`), which creates it, a database of its own, and publishes its
connection under the claim's ID: `<project>.<instance>.<parameter>` for a claim written in
an instance's values (`demo.hive.db`), `<project>.<name>` for a named claim of a
project (`demo.shared-db`)
([okdp-compiler: claims](https://github.com/OKDP/okdp-compiler/blob/main/docs/specs/01_inputs_outputs.md#claims)).
The provider of a claim is the provider of its class, the default one unless the claim
names another (or names its provider); the classes are the platform's and the
projects', `global.okdp.provisioning.<contract>`:

| Contract | Default class | Provider | Per claim |
|---|---|---|---|
| `database-server` | `standard` | `cnpg-system/cnpg-postgresql`, the instance `cnpg-postgresql` of the project `cnpg-system` (the release `cnpg-system-cnpg-postgresql`) | a database, its owner role and the role's credentials (the extensions requested) |
| `s3` | `standard` | `s3-system/s3-minio-provisioner` (the release `s3-system-s3-minio-provisioner`), on RustFS of the bootstrap through MinIO's admin API | a bucket named after the claim's ID, a policy and a user limited to it, the user's generated keys (the paths requested, seeded) |

A project adds classes of its own (its `project.yaml`, `global.okdp.provisioning`), and
changes none of the platform's. A provider of another namespace serves a claim with
its consent: through a class of `platform.yaml`, the platform's routing, always;
through a class of a project, or named by the claim (`{provider:
<namespace>/<instance>}`), only when it lists the claimer's namespace among its
`claimers` (its `instance.yaml`, else its package's `provisions`; `"*"`, every
namespace), else the compile refuses the claim. The sandbox's claims go through the
platform's class `standard`: no provider lists claimers. The provider is of another
namespace than its claimers: the credentials of a claim cross through the platform's
secret store,
`global.okdp.secrets` (OpenBao of the bootstrap, reached through the SecretStore
`okdp-secrets` the compiler writes in each namespace), a `PushSecret` of the provider
and an `ExternalSecret` of the claimer, both written by the compiler, under the key
`<provider's namespace>/<claim ID>` (`cnpg-system/demo.hive.db`). OpenBao's policy,
templated on the namespace that signs in ([`bootstrap/openbao/init.sh`](https://github.com/OKDP/sandbox-charts/blob/main/bootstrap/openbao/init.sh)),
lets the provider write `<its namespace>/*`, a claimer read `+/<its namespace>.*`
(its claims, whichever namespace provides them) and every namespace read
`platform/*`: a namespace never reads another's claims. A claimer's release waits
for its provider's. A claim's
binding is computed at each compile, never stored: a changed default class, or a
class's provider, moves its claims to new, empty connections, the data left where it
was; a provider keeps the data of a claim that is gone.

In the sandbox, the demo project claims its databases (airflow, hive, polaris,
superset): no database is declared by hand. Its buckets are not claims: they are the
platform's S3 store's, a dependency of the platform, created at the bootstrap and named
by the platform connection `platform-s3`, with the platform's identity. A service that
claims a bucket instead (`{}` in place of the connection's name) gets one of its own,
and an identity limited to it, from `s3-system/s3-minio-provisioner`, which creates them
on that same store, RustFS, which OKDP does not manage, as the provisioning identity the
bootstrap generates; the bucket outlives the claim. Keycloak, a dependency too, has its own PostgreSQL cluster, installed
with it at the bootstrap. The compile of the tree binds every claim to its provider, of
whatever namespace: the instances compile together (okdp-compiler's `CompileAll`), as
the control plane server checks a write.

## Compiling: from the tree to compiled/

The tree is compiled whole by okdp-compiler (`LoadRepository`, `CompileAll`,
`NewGraph`): each instance with its package (`catalog/<service>/<version>/` of its
catalog) and the contracts of the catalogs; its context the platform's
(`platform.yaml`), then its project's (`project.yaml`), then its own
(`connections.yaml`); its values its `config.yaml`; under the release `<r>` in the
namespace `<p>`. The parameters are checked against the package's schema, the
connections against their contracts, each claim is bound to its provider, and the
result is an umbrella chart over the package's upstream charts with its values file
`instance.values.yaml` (no chart defaults: Helm applies them), the instance's own
objects, what it publishes and the instances it waits for (okdp-compiler
[docs/01_usage.md](https://github.com/OKDP/okdp-compiler/blob/main/docs/01_usage.md#--output)).
okdp-compiler's Argo CD and Flux targets write the engines' files; okdp-gitops puts
them under `compiled/` as they are, and writes no engine file of its own.

Who compiles: `okdp-gitops compile` ([okdp-gitops](https://github.com/OKDP/okdp-gitops):
`make build`), always the whole tree:
- the CI of the output repository, every 2 minutes and when dispatched: its
  workflow `.forgejo/workflows/okdp-gitops.yaml`, the only one, run by the Forgejo
  Actions runner
  [`forgejo-runner`](https://github.com/OKDP/sandbox-charts/blob/main/bootstrap/forgejo-runner/values.yaml), each run
  a new container of the okdp-gitops image (`okdp-gitops compile`, the topology of
  the workflow, the token of the output repository's `OKDP_GITOPS_TOKEN`, the chart
  cache a volume of the runner's Docker daemon), reads the latest sources, stops when
  they did not move since the last compile (`sources.yaml` of the output), else
  commits the output (`okdp: compile`); a tree that does not compile writes nothing,
  and the run fails (the **Actions** tab of the output repository). The console
  commits the tree only, once its compile passes;
- `scripts/configure.sh --push` runs it on the committed layout and pushes the result
  (the bootstrap);
- `scripts/compile.sh` runs it on the layout as it is, into an output directory, never
  into this one (the output tree is the same in every topology: the output
  repository's content, at its root), with the catalogs read from Git
  ([Service catalogs](#service-catalogs)):

```sh
scripts/compile.sh                          # the tree compiles, or its problems
scripts/compile.sh --output /tmp/okdp-out   # the output tree --push would push
```

It calls `okdp-gitops compile --config <the tree of this directory, the output
directory> --catalog platform-charts=<dir> --catalog sandbox-charts=<dir> --catalog
community-charts=<dir>`. `--root DIR` compiles another layout (a checkout of the
repositories of the sources, put together); `--output DIR` is a directory of its own,
never the layout nor in it: the output is never in a repository of the sources. A
tree that does not compile (an invalid `instance.yaml`, a
package missing from the catalogs, a missing connection, a parameter the package
refuses, a claim no provider binds, a reference to an instance the project does not
have) is reported whole, and nothing is written. The values are checked against each
upstream chart's `values.schema.json` by the control plane server before it commits
(its chart cache, `gitops.chartCacheDir`), by the CI (its `--charts` cache) and by
`scripts/check.sh --helm` (Helm renders every compiled instance; `--charts DIR`, a
cache filled by `scripts/pull-charts.sh`, spares it the network).

## Generated files

Written by the compile into the output repository, under `compiled/`, the files of
okdp-compiler's targets, each marked generated on its first line
([targets](https://github.com/OKDP/okdp-compiler/blob/main/docs/specs/01_inputs_outputs.md#targets)):

| File | Content |
|---|---|
| `compiled/projects/<p>/instances/<r>/Chart.yaml`, `instance.values.yaml` | the umbrella chart (the package's `Chart.yaml`, its dependencies the upstream charts it renders, the OAuth client charts in `dcr` mode) and its values |
| `.../okdp.objects.yaml`, `templates/okdp.yaml` | the instance's objects (its package's, the ExternalSecrets of its claims and of the connections in the secret store, a provider's PushSecrets), rendered by the umbrella as written |
| `.../okdp.info.yaml` | what the instance publishes: its URL, usage and the connections it provides (what the console shows of the instance and offers to the others) |
| `.../application.yaml` | Argo CD: Application `argocd/<r>` (release `<r>`, namespace `<p>`, AppProject `project-<p>`), its source the instance's directory of the repository of `argocd/root.yaml` with `instance.values.yaml`, its sync wave after the instances it waits for; written when the output has `argocd/root.yaml` |
| `.../helmrelease.yaml` | Flux: HelmRelease `okdp-releases/<r>` (release `<r>`, namespace `<p>`), its chart built from GitRepository `okdp-gitops` at the instance's directory, its values from the ConfigMap `values-<r>` alone, `dependsOn` the instances it waits for |
| `.../kustomization.yaml` | Flux: the ConfigMap `values-<r>` of the compiled values file, and `helmrelease.yaml` |
| `compiled/projects/<p>/kustomization.yaml` | Flux: the instances of the project, and `project` |
| `compiled/projects/<p>/project/namespace.yaml` | the Namespace `<p>`, labelled `okdp.io/project: <p>` and with its Pod Security labels: `enforce: privileged` for one of the platform's own projects, else `enforce: baseline`, `audit` and `warn` `restricted`; Argo CD: kept when the project is removed (`Delete=false`), as Flux keeps it (`flux/sync.yaml`) |
| `compiled/projects/<p>/project/secret-store.yaml` | the ServiceAccount `okdp-secrets` (its token not mounted) and the SecretStore `okdp-secrets` of namespace `<p>`, the provider of `global.okdp.secrets.provider` (OpenBao), which the namespace's ExternalSecrets and PushSecrets name |
| `compiled/projects/<p>/project/appproject.yaml` | Argo CD: the AppProject `project-<p>` of the project's Applications, its sources the output repository; namespace `<p>` and no cluster-scoped kind, or every namespace and kind for one of the platform's own |
| `compiled/projects/<p>/project/service-account.yaml` | Flux, a project that is not one of the platform's own: the ServiceAccount `project-<p>` in `okdp-releases`, bound by the Role `okdp-project` to every verb of namespace `<p>` only; the HelmReleases of the project are installed as it (`serviceAccountName`) |
| `compiled/projects/<p>/project/kustomization.yaml` | Flux: the project's manifests above |
| `compiled/projects/kustomization.yaml` | Flux: the projects, the root Flux syncs (`./compiled/projects`) |

A failed action never uninstalls the release: an uninstall stops half-way on the objects
the `okdp.io/protected` policies of the bootstrap (sandbox-charts' `bootstrap/protection`) refuse to delete (CRDs,
Deployments), after their ServiceAccounts are gone. A failed install (`timeout: 15m` per
Helm action, for the slow first installs of a loaded machine) is kept and retried in
place every 2 minutes, without limit (the retry is a Helm upgrade of the failed
release), as Argo CD retries a sync; a failed upgrade is rolled back to the last
deployed release, 3 times at most. A release that never deployed has no rollback
target: when the retry of its install fails as well, the HelmRelease stalls
(`MissingRollbackTarget`) until the next change of its files or `flux reconcile
helmrelease --force`.

### What the server writes, per action

The tree in the platform or project repository, one commit; the CI compiles it into
the output repository, at its next run; the server writes no compiled
file.

| action | tree (the server's commit) | compiled/ (the CI's compile of it) |
|---|---|---|
| deploy instance | `instance.yaml`, `config.yaml` | the instance's directory, the project kustomization (and `project/`, the project's first instance) |
| edit parameters, upgrade (version) | `config.yaml`, `instance.yaml` | the instance's directory |
| delete instance | removes the instance directory | removes the instance's directory, rewrites the project kustomization |
| create/update connection | the entry `connections.<c>` of `project.yaml` (or of `platform.yaml`) | the files of the instances that reference it |
| delete connection | removes the entry (refused while an instance references it) | |
| named claim | the entry `claims.<name>` of `project.yaml` | the files of the provider and of the claimers |
| create project | `project.yaml` (split: the repository `okdp-project-<p>`, then `projects.yaml`) | |
| delete project | removes `projects/<p>/` | removes `compiled/projects/<p>/`, rewrites the root kustomization (the namespace is kept) |
| catalog list | `catalogs.yaml` | |

## Install with Argo CD

Prerequisites: Argo CD (tested with v3.4.2) assessing the health of Applications,
needed by the sync waves (an app of apps waits for Healthy Applications only then),
and, for the sandbox, the sign-in with Keycloak (client `argocd` of the realm,
sandbox-charts' `bootstrap/keycloak/realm.yaml`, PKCE) and the roles of its users:

```sh
kubectl -n argocd patch configmap argocd-cm --type merge \
  --patch-file gitops/argocd/bootstrap/argocd-cm-patch.yaml
kubectl -n argocd patch configmap argocd-rbac-cm --type merge \
  --patch-file gitops/argocd/bootstrap/argocd-rbac-cm-patch.yaml
# argocd-server reads the OIDC TLS setting at startup only.
kubectl -n argocd rollout restart deployment argocd-server
```

1. The files of `argocd/` name the output repository (`scripts/configure.sh
   --topology` sets it). For another Git server, change the URL/branch there and in
   `flux/`, and `gitops.topology` of the server. Commit, push
   (`scripts/configure.sh --push`): okdp-gitops writes the Applications of the
   instances because the output has `argocd/root.yaml`, with its source's repository
   and revision.
2. `kubectl apply -n argocd -f gitops/argocd/`, from this repository: Application
   `okdp` then reads `argocd/` from the output repository.

The entry points' own objects in the engines' namespaces take names no release,
`<p>-<i>` (a DNS label, with a dash), can: `okdp`, `okdp.instances`, `okdp.projects`
and `okdp.project.<p>` in `argocd`, `okdp` and `okdp-gitops` (the source the compiled
HelmReleases name) in `flux-system`, where no project's object can be (the compile
refuses a project of `argocd`, `flux-system` or `okdp-releases`). An Application
`okdp-instances` would be the release of an instance `instances` of a project
`okdp`, which would replace the app of apps and prune every Application it applies.

Argo CD then manages `argocd/` itself (Application `okdp`), and one Application `<r>`
per compiled instance: the `application.yaml` the compile writes in its directory,
applied by the app of apps `okdp.instances` from the output repository
(`compiled/projects`, `*/instances/*/application.yaml`). An instance's Application has
one source, the output repository at the instance's directory (the umbrella chart, its
dependencies fetched from their repositories), `helm.valueFiles:
[instance.values.yaml]`, `releaseName: <r>`, destination namespace `<p>`. Its sync wave
orders it after the instances it waits for. It belongs to the AppProject `project-<p>`
that okdp-compiler writes for the project, `compiled/projects/<p>/project/appproject.yaml`,
applied with the project's Namespace and SecretStore by the Application
`okdp.project.<p>` (ApplicationSet `okdp.projects`, one per `compiled/projects/<p>/`
directory, the files of `project/` as a plain directory, under the entry point's
AppProject `okdp`). The AppProject keeps the project's Applications to the output
repository and, unless the project is one of the platform's own
(`global.okdp.policy.privileged`), to namespace `<p>` with no cluster-scoped kind:
such an Application that writes another namespace or a cluster-scoped object fails
its sync. The namespace is created by the project's manifests (the Applications do
not) and kept when the project is removed (`Delete=false`). `<p>` is the directory
name, never a value read from a file of the project. The
Applications ignore the `caBundle` that cert-manager's cainjector, ingress-nginx's
certgen hook or trust-manager inject after the apply (webhook configurations and CRD
conversion webhooks, `RespectIgnoreDifferences=true`); `compare-engines.sh` ignores it
too. They sync with `ServerSideApply=true` and diff server-side
(`argocd.argoproj.io/compare-options: ServerSideDiff=true,IncludeMutationWebhook=true`:
the objects defaulted by the API server or a mutating webhook, such as CloudNativePG
Clusters or trust-manager Bundles, stay in sync) and retry without limit (backoff up to
5 minutes): an instance may wait for another on a first install. Deleting an instance
directory deletes the Application and its resources (finalizer). The generated
`helmrelease.yaml` and `kustomization.yaml` files are ignored by Argo CD.

## Install with Flux

Prerequisites: Flux (tested with v2.9.5: source-controller, kustomize-controller,
helm-controller), the sandbox's Forgejo holding the repositories
(`scripts/configure.sh --push`), and helm-controller started with
`--feature-gates=DisableChartDigestTracking=true`, so that `.Chart.Version` (the
`helm.sh/chart` label) is the same as under Argo CD:

```sh
kubectl -n flux-system patch deployment helm-controller --type json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--feature-gates=DisableChartDigestTracking=true"}]'
```

(With `flux bootstrap`, add the same patch to `flux-system/kustomization.yaml`.)

1. `flux/sync.yaml` names the output repository (`scripts/configure.sh --topology`
   sets it; for another Git server, as for Argo CD). Commit, push
   (`scripts/configure.sh --push`).
2. `kubectl apply -f gitops/flux/sync.yaml`, from this repository: the GitRepository
   `okdp-gitops`, the namespace `okdp-releases` and the Kustomization `okdp` of
   `./compiled/projects`, the whole compiled tree.

Flux then syncs `compiled/projects/kustomization.yaml`, which lists the projects, each
project's its manifests (`project/`: its Namespace, its SecretStore and, unless it is
one of the platform's own, the ServiceAccount `project-<p>` of `okdp-releases` bound
to namespace `<p>`, which helm-controller impersonates for its releases) and its
instances, each instance's its HelmRelease and values ConfigMap, in namespace
`okdp-releases`; Helm release storage is in the target namespace, which the
HelmReleases do not create. A Namespace is never pruned
(`kustomize.toolkit.fluxcd.io/prune: disabled`, a patch of the Kustomization `okdp`):
a removed project leaves its namespace and its volumes. No `wait`:
one broken instance does not block the others; a HelmRelease waits for the releases it
depends on (`dependsOn`), and is retried until the CRDs of its operator exist. A
package's chart is built from the output repository at every revision
(`reconcileStrategy: Revision`), its upstream charts fetched from their repositories.
Deleting an instance directory uninstalls the release (`prune`): the compile removes
its compiled files.

## Scripts

At the root of the repository, in `scripts/`, run from there. They act on this
directory; `configure.sh`, `compile.sh` and `check.sh` take another layout with
`--root DIR`.

```
scripts/bootstrap.sh              # the platform's dependencies, with helm (README, step 3)
scripts/configure.sh              # engine, topology; --push: compiled, to Forgejo
scripts/compile.sh                # compiles the tree into an output directory, the catalogs from Git
scripts/check.sh                  # CI: the tree compiles, shapes and contracts valid
scripts/pull-charts.sh            # fills a chart cache with the upstream charts (check.sh --helm)
scripts/compare-engines.sh        # compares the live objects of two clusters (Argo vs Flux)
scripts/e2e-kind.sh               # end-to-end install on a throwaway kind cluster
scripts/lib/                      # shared by the scripts (topology, catalogs, Forgejo)
```

- `scripts/bootstrap.sh [--dir DIR] [--catalog NAME=SRC]...`: installs the platform's
  dependencies into the cluster of the current context, the releases of sandbox-charts'
  `bootstrap/charts.yaml` with their values and the steps between them (the CA bundle,
  the deletion protection, the CoreDNS patch, Keycloak's database, OpenBao's init),
  the README's step 3; idempotent. `bootstrap/` is read as the catalogs are (at the
  `ref` of sandbox-charts in `catalogs.yaml`), or `--dir DIR` as it is. Needs kubectl,
  helm, yq v4, jq, awk and git.
- `scripts/configure.sh [-i] [--engine argocd|flux] [--topology io|split]`: sets
  `gitops.engine` of the control plane server; sets the [topology](#topologies).
  Without arguments on a terminal (or with `-i`) it asks, the current values being the
  defaults; `--show` prints them. Edits the layout only. `configure.sh --push
  [--force] [--dry-run]` then compiles the committed layout and puts it, its CI (the
  output repository's workflow, on a schedule, and its topology, the token
  `OKDP_GITOPS_TOKEN` of the output repository only, over `http://` to the hosts of
  `CI_INSECURE_HTTP_HOSTS` only, `*.svc.cluster.local`) and the catalogs on the
  sandbox's Forgejo, the CI runner registered for the output repository only, its
  `main` pushed by `okdp-gitops` alone ([Topologies](#topologies)). Needs
  yq v4; `--push` also git, okdp-gitops, curl, jq and kubectl.
- `scripts/compile.sh [--output DIR] [--catalog NAME=SRC]...`: `okdp-gitops compile`
  of the tree into the output tree DIR (a temporary directory without `--output`), the
  catalogs read from Git; see
  [Compiling](#compiling-from-the-tree-to-compiled). `okdp-gitops` (not a script:
  [okdp-gitops](https://github.com/OKDP/okdp-gitops), `make build`; `OKDP_GITOPS` names
  it).
- `scripts/check.sh [--output DIR] [--catalog NAME=SRC]... [--charts DIR] [--helm]`:
  YAML syntax, file shapes (`platform.yaml`, `catalogs.yaml` and its menu, each
  `project.yaml`, each `instance.yaml` a package of the catalogs, each `config.yaml`,
  `argocd/` and `flux/` reading the output repository of the topology), connection
  contracts (from the catalogs' `contracts/`), sandbox-charts holding the bootstrap
  (`bootstrap/charts.yaml`, which sandbox-charts checks itself:
  `scripts/check-bootstrap.sh`), the tree compiles (into a temporary
  output tree, or `--output DIR`), `kustomize build` of every kustomization of that
  output; `--helm` also runs `helm template` of every compiled instance (its umbrella,
  its dependencies from the `--charts` cache or `helm dependency build`). Needs yq v4, jq, git and okdp-gitops; kustomize and helm
  optional.
- `scripts/pull-charts.sh --output DIR CACHE`: fills the chart cache CACHE with the
  upstream charts the compiled instances of the output tree DIR (`compile.sh --output
  DIR`) render (the dependencies of the compiled umbrellas), in the layout of the compiler's chart cache (`helm pull --untar` under
  `CACHE/<repository>/<chart>-<version>/`), for `check.sh --helm --charts CACHE` (and
  `okdp-gitops compile --charts CACHE`). The packages are not pulled: they are read
  from the catalogs. Needs yq v4 and helm.
- `scripts/e2e-kind.sh up|push|down argocd|flux`: installs the sandbox on a throwaway
  kind cluster: the platform's dependencies (`bootstrap.sh`), then the layout through
  its Forgejo (`configure.sh --push`, the topology `E2E_TOPOLOGY`), with the catalogs of
  `OKDP_CATALOGS` or next to this repository and the control plane and okdp-gitops
  images of your choice (`E2E_SERVER_IMAGE`, `E2E_GITOPS_IMAGE`); then a push of the
  admin to the output's `main` must be refused, and a plain commit of the tree, pushed
  to Forgejo, must be compiled by the next scheduled run of the CI and deployed. See
  its header.
- `scripts/compare-engines.sh`: compares the live objects of releases between an Argo
  CD cluster and a Flux cluster, ignoring engine-specific metadata. See its header.
